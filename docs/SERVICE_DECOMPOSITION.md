## Dependency ownership

The current server instance owns one instance of every stateful store. Domain
services receive those exact instances and never construct stores or caches.

```text
DipTraceService (public MCP Facade; top-level assembly)
├── Settings / Policy
├── DocumentGateway ─────── one target registry and document loader
├── ModelCache ──────────── normalized document snapshots
├── SessionStore ────────── live-session state and working XML
├── TransactionStore ────── transaction state, snapshots, backups, previews
├── PlanStore ───────────── placement/silkscreen plans
├── FindingStore ────────── review reports and findings
├── JobStore / EJM ──────── external-job state and process adapters
├── ExportStore ─────────── export metadata and artifacts
├── BackupStore ─────────── write backups
├── RawPreviewStore (lazy)
├── TrustedProvenanceRegistry (package-owned authority)
└── domain services
    ├── documents, bom, review, discovery, exports
    ├── jobs, external_jobs, routing, placement
    ├── semantic_operations, semantic_engine, synchronization
    ├── xml_writes, scaffolding, transactions, evidence
    └── live_sessions
```

`ServiceContext` is intentionally narrow and frozen. It shares only exact
typed dependencies: `Settings`, `Policy`, `ModelCache`, `TransactionStore`,
`SessionStore`, and `FindingStore`. `DocumentGateway` owns the sole mutable
target registry. The Facade retains compatibility attributes such as
`models`, `transactions`, and `sessions` while passing those same instances
to domain services.

### Shared mutable state

* `SessionStore`, `TransactionStore`, `PlanStore`, `FindingStore`, `JobStore`,
  `ExportStore`, and `BackupStore` persist under one configured state directory
  and keep their existing synchronization and retention behavior.
* `ExternalJobManager` shares the one `JobStore` and owns the configured
  external process budget; it is not recreated by a domain call.
* `ModelCache` is the only normalized-snapshot cache.
* `DocumentGateway.targets` is the only document-id-to-target map.
* `RawPreviewStore` is created lazily through the existing Facade property.
* No domain service imports `service.py`, holds the complete Facade, or creates
  a replacement store, cache, transaction manager, session manager, or safety
  policy.

## Current implementation status

The Facade creates each domain service exactly once. Public method names,
signatures, result structures, exceptions, error codes, warning codes, resource
links, ordering, and the 159-tool MCP registration remain unchanged. Direct
service methods are internal seams, not new MCP contracts. Services remain
synchronous; the server-owned worker-thread boundary is unchanged.

## Extraction roadmap

### Completed in this branch

* Establish the typed `ServiceContext` and single `DocumentGateway`.
* Extract document discovery/read models, BOM/library metadata, review and
  findings, signal-integrity analysis, exports, jobs, external adapters,
  routing/placement analysis, semantic operations, synchronization, raw XML
  writes, scaffolding, transactions, evidence/trust, and live sessions.
* Preserve explicit Facade methods and the existing server thread-offload
  boundary; no MCP tool was renamed, removed, or re-registered.

### Intentionally remaining in the Facade

* Top-level construction and singleton ownership of every store/cache/manager.
* Capability/status reporting, workflow prompt-name registration, and
  compatibility attributes used by the server and tests.
* Narrow safety callbacks for allowed-path resolution, atomic writes, SHA
  gates, provenance sidecars, trust invalidation, and stored-plan apply.

### Next extraction candidates

* Split the remaining plan-application coordinator only if its callback
  surface can stay narrower than the current safety seams.
* Move capability probing into a typed capability assembler only if startup
  output and adapter probe behavior can be characterized completely.
* Continue direct-service parity tests before any further boundary change.

## Parity matrix

| Domain | Direct implementation | Characterization/parity coverage | Side-effect invariant |
| --- | --- | --- | --- |
| Documents | `DocumentService` | service, inspector, bounded payload, connectivity, and facade contract tests | reads preserve cache/state ownership |
| BOM/library | `BomService` | review/library tests and facade complete-payload equality | no transaction/session records for read-only calls |
| Review/analysis | `ReviewService` | review, signal-integrity, impedance, and facade tests | finding persistence remains the existing review side effect |
| Discovery/exports/jobs | discovery, exports, jobs, external jobs services | discovery/export/job/adapter tests | exact shared stores and bounded artifacts |
| Routing/placement | routing and placement services | routing, placement, and plan tests | plan/write gates and ordering preserved |
| Semantic/sync/XML | semantic operations/engine, synchronization, XML writes | semantic, sync, raw-write, and bounded-payload tests | SHA/policy/atomic-write boundaries unchanged |
| Transactions/evidence/sessions | transaction, evidence, and live-session services | recovery, trust, evidence, and live-lifecycle tests | rollback, trust, lease, and session guarantees unchanged |

All dictionary payload comparisons are complete equality comparisons where
fixtures permit them. Exception parity checks retain the original exception
type, stable error code, safe details, and absence of path/traceback leaks.
Read-only checks record state entries before and after calls.
